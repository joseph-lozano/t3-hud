# T3 attention signals for the HUD

Research only; no application changes. Checked 2026-09-18 against upstream commit `9cb586acd0494c4f47f60045ee42ef25edb5a07c`. This is current upstream source, not proof that the deployed app.t3.codes build has these exact features. A real-page compatibility check is required before implementation.

## Existing signal

T3 already computes notification events for completed turns, required input, approvals, and failures. The coordinator runs for every environment returned by the connection catalog, including relay-managed environments; it is not limited to the selected thread. Its pending map is keyed by environment and thread, replaces repeated notifications for that thread, and clears when the web window gains focus. Initial snapshots and reconnect baselines do not replay historic events. This is **notifications since focus**, not a synchronized unread-thread count. [Coordinator](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/components/ThreadNotificationCoordinator.tsx#L20-L84), [event selection and background gating](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/components/ThreadNotificationCoordinator.tsx#L103-L204), [environment catalog](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/state/environments.ts#L25-L57).

The count currently has two outputs: Electron `desktopBridge.setNotificationBadge({count,image})`, or, in the web app, a replacement favicon. The web favicon is a 64×64 PNG containing a red circle and white number, capped at `9+`. Clearing the count restores the original favicon. There is no numeric DOM attribute; copying the badge image avoids trying to OCR or recreate its count. [Badge implementation](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/threadNotifications.ts#L22-L65).

The current notification path requires T3 notification mode enabled, a `Notification` API with granted permission, and successful construction of a Notification while the document is not both visible and focused. Notification mode defaults to off. The settings UI requests permission. Therefore watching the favicon alone is insufficient if WKWebView does not supply the Notification behavior T3 expects. [Gate](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/components/ThreadNotificationCoordinator.tsx#L169-L198), [settings](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/components/settings/NotificationSettings.tsx#L34-L66), [default](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/contracts/src/settings.ts#L290-L295).

## Integration choices and constraints

1. **Wrapper-only compatibility experiment:** provide a scoped browser Notification adapter if necessary, preserving T3's titles, tags, close, and click behavior. Observe T3's generated favicon and send the bounded PNG to Swift for a small badge overlay. Let T3 own its pending map and clearing rules; add no native unread store, second server connection, or environment discovery. A badge-only adapter must explicitly describe its in-app permission semantics; it must not pretend macOS has granted system-notification permission. Actual API/focus behavior needs a WKWebView test before committing to this route. This is an inferred feasible approach, not an existing supported extension API.
2. **Cleaner upstream seam:** add an optional, browser-safe badge/event callback in T3's notification module. This would expose count directly without favicon parsing and could emit events independently of desktop Notification permission. That requires changing and deploying T3's UI, so the wrapper alone cannot use it today. Do not promise an upstream change will appear on hosted T3 Connect.
3. **Avoid a fake partial desktopBridge.** Its presence is how T3 detects Electron and changes runtime behavior. The optional badge methods exist, but are part of the larger desktop IPC interface rather than a standalone public HUD interface. [Detection](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/env.ts#L1-L6), [interface](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/contracts/src/ipc.ts#L1096-L1103).

## Why not count sidebar dots or page titles?

T3's sidebar completion marker is a separate local UI concept based on `lastVisitedAt`. The selected mounted ChatView stamps a completion visited in an effect without a focus/visibility guard, so mirroring sidebar dots can miss a completion received while the HUD is hidden. Filtering/collapsing sidebar rows can also make DOM counts incomplete. Its title synchronizer contains branding/version information, not notification counts. [Unseen completion logic](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/components/Sidebar.logic.ts#L635-L644), [ChatView visited effect](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/components/ChatView.tsx#L2107-L2125), [local persistence](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/uiStateStore.ts#L161-L180), [document title](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/web/src/routes/__root.tsx#L319-L333).

Targeted source searches found no existing browser service-worker notification or `setAppBadge` integration in apps/web/src. This is a bounded source observation, not a guarantee of absence in future builds. The inspected current interfaces provide no standalone documented badge subscription endpoint for external wrappers; building a new RPC client would move beyond simply wrapping the UI.

## Acceptance checks before shipping

- Verify deployed T3 Connect actually contains this notification implementation.
- Confirm completion/input/approval/failure from two connected environments reach the adapter with HUD hidden; verify the selected thread too.
- Confirm count is per thread, caps at 9+, and clears through T3's normal focus behavior.
- Confirm reload/reconnect does not replay old completions, and loss of connection does not imply a fresh count of zero.
- Confirm no notification when T3 settings say off; distinguish badge permission from any later optional system notification permission.
- Confirm icon dragging, click toggling, fullscreen overlay, and focus restoration remain intact.
- Validate message origin/main-frame, payload size/type, and data image decoding. Only accept trusted T3 origins; no credential or thread-content extraction is needed for an image-only badge.

## Native implementation and proposed sequence

The current floating icon is an AppKit NSButton with custom drawing in `Sources/T3HUD/FloatingIcon.swift`; a small top-right badge image can be drawn without changing its existing drag/click behavior. The current HUD keeps its WKWebView alive when hidden. Apple's [WKScriptMessageHandler](https://developer.apple.com/documentation/webkit/wkscriptmessagehandler) supports passing page messages to native code. A small scoped script can observe favicon changes and forward supported notification events; this does not require a second connection to T3's backend.

Herdr's reference implementation uses a native nonactivating NSPanel next to its icon for silent alerts, only while its main panel is closed. It dismisses after eight seconds, retains on hover, and offers click-through. This is a suitable UI model, but its separate unread Set should not be copied into this wrapper. [Native badge/toast dispatch and panel](https://github.com/finna/herdr-hud/blob/503280d31826fdaa7c2756dac16291ff5b9b8337/Sources/HerdrHUD/App.swift#L186-L242), [Herdr unread state](https://github.com/finna/herdr-hud/blob/503280d31826fdaa7c2756dac16291ff5b9b8337/Sources/HerdrHUD/Resources/app.js#L1-L70).

Recommended sequence, subject to user approval:

1. Prove the existing deployed UI's notifications, WKWebView Notification availability, and hidden-window focus/visibility behavior. Use disposable work so no real prompts are sent without approval. Stop and report if reliable host integration needs upstream changes.
2. Add explicit opt-in HUD notification support. Where needed, adapt the subset of browser Notification used by T3, including permission, tag/replacement, close and click callbacks. Describe permission as HUD alerts, not system notification authorization. Keep T3's own notification mode in control.
3. Mirror T3's generated badge image at the icon's upper-right corner. Keep no independent unread database, and let T3 clear the badge on focus. A stale/disconnected signal must not be presented as a newly confirmed zero.
4. Add silent Herdr-style popups near the icon while hidden, without taking keyboard focus. Clicking opens the HUD and invokes T3's notification click behavior. Coalesce repeated updates and do not replay historical events on reconnect.
5. Verify selected/background threads, multiple environments, focus clearing, settings off, reconnect, icon dragging and fullscreen placement. Capture real user-facing evidence before shipping.

Optional later: macOS Notification Center alerts using [UNUserNotificationCenter](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app), with separate [system permission](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications). An in-app badge/popup does not need that OS notification permission. This design only observes new T3 events while the HUD process and its web connection are alive; it does not add a push service for a quit or sleeping app.

No implementation, app installation, or notification permission change was performed during this research.

## Existing server API: a viable alternative

Follow-up research: T3 already exposes the server facts needed for a native attention indicator. The lack of a standalone *badge-count* endpoint does **not** mean there is no API route:

- `GET /api/orchestration/shell` supplies projects and thread summaries. The handler requires orchestration read authorization. [HTTP client path](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/client-runtime/src/state/shellSnapshotHttp.ts#L25-L40), [read-scoped handler](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/apps/server/src/orchestration/http.ts#L50-L60).
- Streaming RPC `orchestration.subscribeShell` returns snapshots and subsequent thread/project updates. A sequence cursor supports catch-up; clients must handle synchronization and snapshot fallback. [RPC](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/contracts/src/rpc.ts#L1304-L1309), [events and cursor](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/contracts/src/orchestration.ts#L920-L974).
- Thread summaries include latest turn, session, pending approval/input flags, actionable plans, and optional background activity. These can support a count of threads **currently requiring attention** without inventing backend facts. [Fields](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/contracts/src/orchestration.ts#L875-L902).

A native API consumer is therefore technically viable without changing T3's server. It is a larger wrapper change: maintain one authenticated subscription per environment, reuse or integrate T3 Connect's authorization and discovery, and handle reconnect/version compatibility. The existing runtime already wraps authenticated HTTP and the optional managed-relay DPoP signer; replacing that with a plain unauthenticated poll would not work for protected remote environments. [Runtime authentication use](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/packages/client-runtime/src/state/shellSnapshotHttp.ts#L9-L40).

A compact read-only attention endpoint could be added upstream if reducing coupling and payload is worth modifying T3. It should return server-known facts (thread IDs, state, turn/completion identifiers), not claim to know which notifications this HUD has seen. “Completed since I last looked” still needs a client acknowledgment boundary or a new server-side per-client read model. The current notification count remains web-client state, as described above. This is the design choice to settle before implementation: current attention versus notifications since focus.

Relay also has agent-activity publishing and mobile delivery machinery, but the inspected publisher is an internal service targeting APNs/FCM and live activities, not evidence of a ready public macOS badge subscription. Do not treat mobile push registration as a simpler generic HUD API without further contract review. [Publisher service](https://github.com/pingdotgg/t3code/blob/9cb586acd0494c4f47f60045ee42ef25edb5a07c/infra/relay/src/agentActivity/AgentActivityPublisher.ts#L33-L68).
